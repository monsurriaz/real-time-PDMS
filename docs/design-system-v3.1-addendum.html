01 — Decision

Footer: public pages only

The question was whether an app with a sidebar needs a footer. It doesn't — a footer exists to carry secondary navigation and legal links when there's nowhere else to put them, and the rail already owns navigation. Two navigation systems on one screen is the thing that reads as dated.

The rule. Public pages (/, /login, /signup, /track/:id) get a slim dark footer. Authenticated screens behind the rail get none — the workspace scrolls to its content and stops. This is what every serious ops product does, and it's why adding a footer to the admin board would make it feel more like a website, not less.

Search. Filters the current screen's rows client-side over data already fetched — no new endpoint, no new index. The placeholder names what it searches on this specific screen rather than implying global search. Bind ⌘K / Ctrl+K to focus it.
Notifications. Built from data that already exists — recent status:changed events for parcels this user can see, plus overdue alerts for admins. Scoped by the same role rules as everything else. The unread dot only appears when something is genuinely unread.
The header avatar should be deleted, not wired up. The rail's account block at the bottom already owns identity, Profile, and Log out. A second account menu in the header is two doors to one room — it's the kind of redundancy that makes an interface feel assembled rather than designed. If identity must appear in the header, it belongs there instead of in the rail, not as well.

05 — Fix

Lifecycle rail — two variants

At 86px wide, five segments with 3px gaps become 14px dashes that read as an ellipsis rather than progress. That's a real legibility failure in the busiest place the component appears.

Compare at table width
Now — reads as dashes
Compact — one continuous track
Two named variants, one component. rail="full" keeps five discrete segments for detail views, agent cards, and the landing showcase, where there's room for each stage to be its own object. rail="compact" renders a single continuous track filled to the current stage and coloured by it — used in every table row. Same data, same props, chosen by available width, not by guessing.

06 — Bug

Map rendering

The screenshot shows the route as disconnected blue dashes with a hollow marker and no visible rider. That isn't a styling preference — something is wrong in the implementation.

Correct rendering
Four rules. Completed route is a solid 4px accent line — the current dashed-everything is the visible bug. Remaining route is dashed at ~45% opacity. The rider is an accent disc with a soft accent halo, always z-ordered above both endpoint markers. Pickup is a solid ink dot, drop-off an ink pin — never hollow, since a hollow marker reads as a disabled state.
